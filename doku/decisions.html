Dokumentation · Version 0.1.0

Warum wurde es so gebaut?

Diese Seite dokumentiert zentrale Entscheidungen, die während der Entwicklung von KIEZFIT getroffen wurden. Sie beschreibt nicht nur das Ergebnis, sondern auch die Gründe und Auswirkungen der jeweiligen Entscheidungen.

01

Statisches Frontend als Grundlage

Entscheidung

KIEZFIT wurde zunächst als statische Website mit HTML, CSS und JavaScript umgesetzt.

Begründung

Die visuelle und technische Grundlage sollte zuerst stabil aufgebaut werden, bevor Backend, Benutzerkonten und dynamische Funktionen hinzukommen.

Auswirkung

Version 0.1.0 bleibt überschaubar, schnell testbar und bildet gleichzeitig die Grundlage für spätere Ausbaustufen.

02

CSS auf mehrere Dateien aufgeteilt

Entscheidung

Die Styles wurden auf fünf CSS-Dateien verteilt: Base, Layout, Components, Sections und Responsive.

Begründung

Eine klare Trennung erleichtert Wartung, Fehlersuche und spätere Erweiterungen.

Auswirkung

Änderungen können gezielter vorgenommen werden, ohne eine einzelne große CSS-Datei bearbeiten zu müssen.

03

Zentrale CSS-Variablen

Entscheidung

Farben, Abstände, Schriftgrößen, Radien und Übergänge werden zentral über CSS Custom Properties definiert.

Begründung

Wiederkehrende Werte sollen konsistent bleiben und sich später möglichst an einer zentralen Stelle ändern lassen.

Auswirkung

Das Design besitzt ein einheitliches Wertesystem und kann in zukünftigen Versionen leichter weiterentwickelt werden.

04

Dunkle Farbwelt mit Lime-Akzent

Entscheidung

Carbon, Graphit und Off-White bilden die Grundlage. Lime wird als gezielter Akzent eingesetzt.

Begründung

Die Kombination unterstützt den sportlichen und modernen Charakter der Marke und schafft gleichzeitig eine klare visuelle Hierarchie.

Auswirkung

Interaktive Elemente und wichtige Inhalte lassen sich schnell erkennen, ohne das gesamte Interface mit Akzentfarbe zu überladen.

05

Textbasierter Schriftzug als Logo

Entscheidung

Das KIEZFIT-Logo wurde als HTML-Text umgesetzt und nicht als Bild eingebunden.

Begründung

Der Ansatz benötigt keine zusätzliche Bilddatei, ist skalierbar und lässt sich direkt über CSS gestalten.

Auswirkung

Das Logo bleibt leichtgewichtig und kann später ohne Austausch einer Grafik angepasst werden.

06

Individuelle Studio-Landkarte

Entscheidung

Der Studio-Bereich wurde nicht als gewöhnliches Kartenraster, sondern als visuelle Studio-Landkarte gestaltet.

Begründung

Ausstattung, Community, Atmosphäre und Betreuung sollen als zusammengehörige Bestandteile des Studios wahrgenommen werden.

Auswirkung

Der Bereich erhält eine eigenständige visuelle Identität und unterscheidet sich bewusst von den standardisierten Kartenrastern der anderen Abschnitte.

07

Responsive Design über Media Queries

Entscheidung

Die Website passt sich über mehrere Breakpoints an unterschiedliche Bildschirmgrößen an.

Begründung

Desktop, Tablet und Smartphone sollen dieselbe Website nutzen und dabei jeweils sinnvoll angeordnet werden.

Auswirkung

Navigation, Grids, Karten und Buttons verändern ihre Anordnung abhängig von der verfügbaren Bildschirmbreite.

08

JavaScript bewusst schlank gehalten

Entscheidung

Für Version 0.1.0 wird kein Framework eingesetzt. JavaScript übernimmt nur die benötigten Interaktionen.

Begründung

Die vorhandenen Funktionen sind überschaubar und lassen sich mit Vanilla JavaScript direkt und verständlich umsetzen.

Auswirkung

Es entstehen keine zusätzlichen Framework-Abhängigkeiten und die bestehende Logik bleibt leicht nachvollziehbar.

09

WebP für große Bildassets

Entscheidung

Große Website-Bilder wurden für die produktive Nutzung als WebP-Dateien optimiert.

Begründung

Die Bilddateien hatten einen relevanten Anteil an der Gesamtgröße der Website und sollten ohne sichtbaren Qualitätsverlust verkleinert werden.

Auswirkung

Hero- und Studio-Bild konnten deutlich verkleinert werden, wodurch die Ladeeffizienz verbessert wurde.

10

Accessibility bereits in 0.1.0

Entscheidung

Barrierearme Grundlagen wurden bereits während der Umsetzung berücksichtigt.

Begründung

Accessibility sollte nicht erst nachträglich ergänzt werden, sondern Bestandteil der grundlegenden Umsetzung sein.

Auswirkung

Unter anderem werden semantische HTML-Strukturen, ARIA-Attribute und sichtbare Fokuszustände verwendet.

11

GitHub als Entwicklungs- und Versionsplattform

Entscheidung

Entwicklung, Issues, Milestones, Pull Requests und Versionsstände werden über Git und GitHub organisiert.

Begründung

Änderungen sollen nachvollziehbar bleiben und einzelne Entwicklungsaufgaben klar voneinander getrennt werden können.

Auswirkung

GitHub bildet die vollständige technische Aufgaben- und Commit-Historie des Projekts ab.

12

Login und Mitgliederbereich bewusst verschoben

Entscheidung

Login, Mitgliederbereich und die vorbereiteten Unterseiten werden nicht als fertige Funktionen Bestandteil von 0.1.0.

Begründung

Zuerst soll die öffentliche Website als stabile Grundlage fertiggestellt werden. Dynamische Funktionen benötigen später eine eigene technische Basis.

Auswirkung

login.html und die Dateien unter pages/ dienen zunächst als Vorbereitung für zukünftige Versionen.

13

Bekannten CSS-Punkt für 0.1.1 zurückgestellt

Entscheidung

Die fehlende Definition von --color-card wird nicht mehr in Version 0.1.0 geändert.

Begründung

Die aktuelle Version soll stabil abgeschlossen werden. Eine technische Bereinigung kann kontrolliert in der nächsten Version erfolgen.

Auswirkung

Der Punkt ist als bekanntes technisches To-do für Version 0.1.1 dokumentiert und wird nicht vergessen.

Übergeordnete Entwicklungsprinzipien

Schrittweise entwickeln Funktionen werden in klar abgegrenzten Entwicklungsphasen umgesetzt.
Bestehendes nicht unnötig verändern Bereits funktionierende Bereiche werden nur geändert, wenn ein konkreter technischer oder gestalterischer Grund besteht.
Zukunft vorbereiten Die aktuelle Version bleibt überschaubar, soll aber spätere Erweiterungen technisch und strukturell ermöglichen.
